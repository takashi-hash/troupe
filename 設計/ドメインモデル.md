## 1. これは何か

**汎用の「自律する仕事場」。** AI の Manager と Worker が Ledger を囲み、Human が判断する。

- エンジンはローカル LLM（外部にデータを送らない）
- まず1台で動く（複数台への拡張は「Participant の Location」という概念だけ確保しておく）
- Custom は順に入れる: **① Ichiza 自身の運転（自己ホスト）② クリニックの庶務（非診療）③ 訪問診療**。
  失敗の軽い題材で仕組みを磨いてから、重い題材に進む。**Foundation はどの Custom の中身も1行も知らない**

---

## 2. 公理

> **判断は Human。**
> AI から排除するのは「人の記憶」と「人の着手」への依存であって、人の判断ではない。
> 判断が要る場所に判断が残っているのは自律の失敗ではない。
> **判断以外のものが人に残っているのが失敗。**

---

## 3. 役割（3つ）

### Manager（1体）
Ledger を回す。**手を動かさない。判断もしない。** LLM も原則使わない（Reconciliation と日付演算だけ）。

勝手にやること（判断ではないから）:
- **Job を作成する** — Definition と Source の Reconciliation で。人が思い出す必要がない
- **Progress を見回る** — 止まっているもの・Deadline が近いものを把握する
- **Closed を確かめる** — Evidence で閉じる。報告を待たない
- **Failure に気づく** — Environment の失敗は再試行する。申告と記録の Discrepancy を見つける
- **Discrepancy を並べる** — 「A の Source にはこうあるが B の Source に無い」

絶対にしないこと（判断だから）:
- **Definition を enact する** — Proposal までは書く。enact するのは Human
- **Checkpoint を approve する** — 担当した Human しかできない
- **不可逆の操作** — Checkpoint を approve 済みでなければ実行しない
- **却下を蒸し返す** — 人が要らないと言った Proposal を再提案しない

Human に差し出すこと:
- **MorningSheet** — 今日見るべきものだけ。毎回同じ Alert は出さない（読まれなくなる）
- **判断の材料** — 決めるのに要る事実を並べる。決め方は言わない

### Worker（N体）
CapabilityDeclaration を出して（どの LLM・Sensitivity の可否・何を受けるか・どの ReadPort・WritePort・Tool に手が届くか）、Job を take し、実行する。
LLM を使うのはここ。Review する係も Reception もいる（書く係と Review する係は別）。
**Reception** — Human の Utterance を仕分ける Worker: Instruction は Job に、業務の追加は Definition の Proposal に写し、質問には Ledger から答える。元の Utterance を Evidence として引用する。
**増やすときは「新しいプロセス」ではなく登録が先。**

### Human
- **判断する** — Checkpoint を approve する・Definition を enact する
- **実行もする** — Agent に手が届かない Job（外部システムでの作業など）

Human は「承認ボタン」ではなく、**Worker でもある**。
これを忘れると、人がやる Job（請求・届出のような）がモデルから漏れる。

## 4. 通信の掟

> **誰も直接話さない。全部、Ledger 越し。**

- Manager → Worker に Instruction は飛ばない（Worker が Ledger から take する）
- Worker → Worker の受け渡しも Ledger 経由（Artifact を次の係が Ledger で拾う）
- Human との Conversation も Ledger に落ちる（**Instruction は必ず Job が作成される** — 口約束が消えない。
  作成するのは **Reception**——聞き取りには LLM が要るから、Manager ではない）

理由: Worker が1体死んでも Job は消えない。誰が何をしたかが常に1箇所に残る。

## 5. Job の一生

```
Inception   3つの道で作成される（人が思い出して作るのではない）:
            ① Definition×Source の Reconciliation — Calendar も Source の一つ
              （時が来たら作成される Job はこれ）
            ② Human の Instruction — Reception が Job に写す
            ③ ChildJob — Running の Job が生む。親の AcceptanceCriteria の内側なら
              Proposal なしで作成される。外に出るなら Proposal
Ready       時刻・前提が揃うまで Agent は take できない（Human はできる）。
            Job は Briefing を携える — Briefing の無い Job は dispatch できない
            ・Instruction で作成される Job は 着手可能時刻＝指示の時（無ければ今）
            ・急ぎは 着手可能時刻＝今・Deadline＝今日 で表す。**緊急フラグは作らない**
              （第2の宣言は Deadline とズレて事故る。2つの時刻で足りる）
Running     Agent が Lease を take して作業。落ちたら Lease が切れて戻る。
            Progress を Event として刻む（黙って空転しない）。Budget を超えたら Failure。
            手に負えないと分かったら、Lease は自分から release する
AwaitingAnswer  材料が欠けたら Human に inquire して止まる。answer が来たら続きから。
            Inquiry で判断は求めない（それは Checkpoint）。答えは Evidence に残る
Verification  2種類ある:
            ・Check — 機械。決定的（白黒つく）。**止める力を持つ**
            ・Review — LLM による。差し戻せるが、その判定が信頼されるには
              **AgreementRate という実測が要る**（信頼は宣言ではなく獲得するもの）
Checkpoint  Human の判断待ち。**担当した人しか approve できない。**位置は Definition が決める
Confirmed   判断済み・まだ外に出ていない（押し間違いから戻れる最後の地点）
Apply       外に出る。**不可逆はここだけ。**主体（Human か Agent か）は Definition が決める。
            **適用が要るかも Definition が決める**——外に出るものが無いタスク（確かめて
            報告するだけ等）は、承認済みから直に完了へ。効かない段を通さない。
            不可逆な Apply は、Checkpoint なしを許さない。
            二相でやる: 先に Attempt を記す → 外に出す → 結果を記す。
            Attempt だけ残して落ちていたら、勝手にやり直さず Human へ
Closed      **Evidence で閉じる**（人の報告に頼らない）。
            Evidence の ReadPort が無い Job は SelfReport＋期限つきの Discrepancy Alert
Failure     ・Environment の失敗 → 自動で再試行（使用上限つき）
            ・Content の失敗 → Human へ
            ・Checkpoint の追い越し → 現実は止めないが、**事故として記録し赤く見せる**
```

## 6. 概念（汎用コア）

```
Participant  Human（RoleDeclaration）／Agent（CapabilityDeclaration）
             ★申告と実態のずれが最大の事故源。起動時に申告と Board の言葉を照合して
             announce する
Ledger       Job の場。Board は Constitution を持つ（目的・非目標・AcceptanceCriteria・言葉）
Gate         Constitution が Human に freeze されるまで、下流の Job は dispatch されない
Definition   Job を生む規則。Version を積むだけ（上書き無し）。AI は Proposal まで。
             Human だけが enact する
Job          §5 の一生を生きるもの
Artifact     Job が生んだもの。Ledger に置かれ、次の係が拾う。Evidence が指す先
Briefing     Job 1件が携える文脈 — 読むべき Source・材料・Artifact の置き場・
             AcceptanceCriteria。Agent は毎回まっさら。Briefing の無い Job は dispatch できない
ChildJob     Running の Job が生む Job。親の AcceptanceCriteria の内側でだけ
             Proposal なしで作成される
Progress     Running の Job が刻む観察。「止まっている」を Manager が見る材料
Budget       1つの Job に使ってよい量と時間。Definition が決める。超えたら Failure。
             ChildJob の Budget は親の残りから切り出す——連なり全体でも親を超えない
Source       一次情報。ReadPort だけ。1つ落ちても他は回る。WritePort は別物として隔離。
             Calendar も Source の一つ
Tool         Agent が作業の途中で自由に使える外への口。**Reversible に限る。**
             Irreversible は Tool ではなく WritePort（Apply の二相と Checkpoint を通る）
Event        観察。判断しない。Source どうしの Discrepancy だけが Human に上がる
Evidence     引用・Fingerprint・Closed の根拠。「なぜそうしたか」を後から説明できる
Conversation Human も Participant。Instruction は必ず Job が作成される
Inquiry      Agent から Human への、材料の欠けを埋める問い。判断は求めない（それは
             Checkpoint）。答えは Utterance で返り、Evidence に残る
Proposal     AI 発の Definition 変更・Job。Human が enact するまで有効にならない。却下は再発しない
Alert        判定は1箇所、画面は並べるだけ。
             ReadPort が無い Evidence を待って鳴らさない（狼少年を作らない）
```

## 7. 不変条件（I1〜I8）

| | 名前 | 意味 |
|---|---|---|
| I1 | 抜けない | Source に存在する義務は必ず Ledger に作成される |
| I2 | 止まる | Checkpoint は担当した人しか approve できない |
| I3 | 通る | 判断のあとに、判断以外の人手作業が残らない |
| I4 | 消えない | Agent が死んでも Job は残り、再開される |
| I5 | 説明できる | どの判断も、根拠と経緯を後から辿れる |
| I6 | 壊れたら気づく | Check は「壊すと赤くなる」ことまで検証されている |
| I7 | 属人化しない | 特定の人の記憶に依存しない |
| I8 | 動き続ける | Agent が起きていて、落ちたら戻る。**起動も自律の一部** |

## 8. Generic と Custom の線

> **仕組みは Generic、中身は Custom。** Foundation は Custom の中身を1行も知らない。

| Generic（Ichiza 本体） | Custom（例は訪問診療——3番目の Custom。線の説明に一番濃い例だから使う） |
|---|---|
| Job の一生・Checkpoint という概念 | Checkpoint の位置（院長の approve・医師の承認済み） |
| Definition の Version・Gate・Proposal | Definition の中身（業務カタログ21項目・Deadline・根拠） |
| Verification の2層という構造 | Check の中身（出典の実在・宛先違い・反転・定型句） |
| Source の ReadPort・Evidence・Discrepancy | Source の種類（カルテ・レセコン・支払基金） |
| Sensitivity という概念と持ち出し制限の仕組み | 何が Sensitivity か（PHI の業務ルール・伏せ字の規則） |

## 9. 血で覚えた教訓（設計原則に昇格）

実際に踏んで直した失敗から昇格させたもの。Ichiza では最初から原則とする。

1. **宣言に執行者がいなければ、それは実装ではない** — 読む者のいない欄、呼ばれない関数、定義ファイルの無い「launchd が面倒を見る」
2. **「変わらなかった」は安全の証拠にならない** — 値を変えたら結果が変わることをテストで固定する
3. **未記録と0件を混ぜない。母集団の違う数字を並べない**
4. **信頼は宣言ではなく実測で獲得する** — LLM の判定・seed の再現性・捨て1回の効果、全部測ってから使う
5. **効かない機能は残さない** — 「一応入れておく」は、次の人が効くと思って使う分、無いより悪い
6. **名指しの一覧より、宣言から導く** — 一覧は新しい型を知らない。規則は Definition から導けば知っている
7. **狼少年を作らない** — 毎回鳴る Alert・出るはずのない Evidence 待ちの Alert は、読まれなくなった時点で嘘になる
8. **申告と実態を照合する** — CapabilityDeclaration が嘘だと、Job の割当てが壊れる
9. **Alert の出口は1本** — 画面ごとに判定すると、出ない画面が「無い」という嘘をつく
10. **消す前に測る** — 寄与ゼロを実測してから消す。「たぶん要らない」で消さない

## 11. 未決（決める場所つき）

> **決め先の無い未決は積まない。** 未決の執行者は「決める歩」。
> 歩が来たら決めて、結論はその歩の成果物に書き、この表から消す。

| # | 未決 | 決める場所 |
|---|---|---|
| 5 | **複数台** — Participant の Location・Ledger の共有 | 決めない（まず1台が決定済み） |
| 10 | **「起きていない Agent」を何で決めるか** — 名簿は帳簿に載るようになった（2026-08-21）。残るのは判定だけ——最後の出来事から何時間で「起きていない」とするか。しきい値は方針（Constitution）か業務ルールか、それとも札の期限から導くか | 働き手が2機以上になる歩。**それまで数字を決め打ちしない**——根拠の無いしきい値は狼少年を作る |
| 11 | **源どうしの Discrepancy を、どこで宣言するか** — 複数の源を読む仕組みは在る（source_refs は並び、Evidence は Reading を持つ）。無いのは「この源とこの源は一致すべき」という**宣言の場所**。版の欄か、方針か | 源が2つ以上要る業務ルールが出てきたとき。**Foundation のコードではなく Custom のデータに置く**（一致の中身は題材ごとだから） |
| 12 | **有効化を解く道が無い** — 出来事の種が無く、帳簿の門が拒む。そのため「有効な業務ルール」と「すべての業務ルール」はいま同じ集合 | 提案（Proposal）を実装する歩——却下と有効化解除は同じ形になる |
| 9 | **担当の引き継ぎ** — Checkpoint の担当が不在のとき | 決めない（まず1人。人が増えたら） |
