14枚を5枚にした。**1つの概念が6枚に散っていたのが、ロールプレイ4回とも通らなかった原因**。

## 2. 書式の掟

### 掟1 — 1行に、主張・執行者・壊しかた
**執行者の欄を空にできない。** 無いなら「まだ居ない」と書く。
**壊しかたが書けないなら、無理に書かない**——書けないと書く（列を埋めるために書いた壊しかたが、正しい実装を赤にしたことがある）。

### 掟2 — 分類には義務が付く
「これは値」と書いたら、**そのままテストになる文**を隣に置く。義務が空の行は分類していないのと同じ。

### 掟3 — 数えるものは、正本を1つ
見出しに数を書かない。他の文書の数を書かない。参照するだけ。

### 掟4 — 語は業務の語だけ
パターンの名（値オブジェクト・集約・ドメインサービス・ファクトリ・リポジトリ・
アプリケーションサービス・プレゼンテーション）は**日本語の定訳のまま**使い、
**用語集には載せない**。役割の語を日本語にすると、そこからコードの名前を作ってしまう。

### 掟5 — 中核と集約は「守るべきもの」から導く
中核は**業務の判断が要るものだけ**。手順と技術は入らない。
集約は「**境界が要る**」と言えた不変条件からしか作らない。

### 掟6 — 層は「置いてはいけないもの」を先に書く
「業務の規則を置いてはいけない」を、中心以外のすべての層に書く。

### 掟7 — 仕掛けは「壊して赤を見た」まで書いて完成
確かめていないものは「置いた」と書かない。**儀式そのものが嘘をつく**ことがある。

### 掟8 — 出典を載せない
### 掟9 — 設計ファイルは和名・全部 .md・`設計/` 直下

## 4. 層

**依存は内向きのみ。** これがオニオンの主張の全部。

| 層 | **置いてはいけないもの** | 置くもの |
|---|---|---|
| **domain**（中心） | **時計・乱数・保存・画面・外の道具**。「いま」は引数で受け取る | 値オブジェクト・エンティティ・集約・不変条件・ドメインサービス・仕様・ファクトリ・出来事の名前・Repository と Store の宣言 |
| **app** | **業務の規則** | アプリケーションサービス（数の正本は[仕事が回る筋道 §1](仕事が回る筋道.md)）・トランザクション境界・DTO への詰め替え・Port と Reader の宣言 |
| **adapters** | **業務の規則** | 帳簿の実装・Port の実装・**腐敗防止層（ACL）** |
| **ui** | **業務の規則** | 画面の部品。**domain を知らない**——プレゼンテーション（橋渡し）は app の入り口（**文字で受けて値に組む**）と DTO |

### コンテキスト

いま1つ。名前は「一座」。**働き手としての AI は中**。

外にあるのは——**題材**（注ぐだけ）・**源**（腐敗防止層で翻訳）・
**LLM の道具**（腐敗防止層で翻訳）・帳簿・時計・画面。

**源と LLM の両方に腐敗防止層（ACL）を置く。** どちらも外の言葉で、中の語へ翻訳されてから入る
——LLM の応答は印つきの `Reply` へ（**振り分けるのは domain の仕様**）、源の中身は**材料・引用・読めなかった理由**へ。

### ロック

| もの | どこ | なぜ |
|---|---|---|
| 楽観ロック | **adapters の中に隠す** | 業務の語ではない |
| 担当が誰か | domain | 業務の語 |
| 期限で担当を外す | app | 排他制御の仕掛け |

## 5. フォルダ

| パス | 何が住むか |
|---|---|
| `main.py` | 組み立ての根。層に属さない。**具体を注ぐのはここだけ** |
| `domain/obligations.py` | 全部に共通の義務。**概念を持たない唯一のファイル** |
| `domain/value_objects/` | 値オブジェクト——people・calendar・rule・job。**1値1ファイル** |
| `domain/aggregates/` | 集約——job（root `job`・一生 `life`・**1操作1ファイル**）と rule |
| `domain/events/` | ドメインイベント——job・rule。1出来事1ファイル。**操作が刻む** |
| `domain/services/` | ドメインサービスと仕様——検査・振り分け・reconcile |
| `domain/repositories/` | リポジトリの宣言——Repository・Store を1宣言1ファイル。**書き込みの門（I1）** |
| `app/ports/` | Port・Reader の**宣言**——1宣言1ファイル。**注ぎ口はここだけ** |
| `app/services/` | アプリケーションサービス——**起こす者のフォルダ**（human・agent・clock・screen）に1操作1ファイル＋`refusal`（**断り**——全操作の返り）。**判断を運ぶのは human だけ**（数の正本は[仕事が回る筋道 §1](仕事が回る筋道.md)） |
| `app/dto/` | **DTO**——出る向きと入る向き（欄の正本は[人に見えるもの §2](人に見えるもの.md)——数をここに書かない）。**文字と ID だけ** |
| `adapters/` | 実装——帳簿・題材・時計・採番・**診療録の口（`emr`——よそのコンテキストの写しの読み手と、下書き受けへの配達。署名済みに書く口は無い）**。**帳簿の実装は手元（SQLite）とクラウド（Cloud SQL）、口は1つ**。**腐敗防止層（ACL）は `acl/` に隔離**——外の言葉を翻訳する2枚（llm・source）だけが住む（llm の中身は Ollama と Gemini）。ほかはただの口 |
| `ui/` | **画面**——1画面1ファイル（今日・予定・履歴・詳細・検索）＋**器**（`shell`＝机の窓・`web`＝web の窓。**どちらも脈を持たない**）＋`words`（操作の語の橋——**正本は1つ**）。**入っているものを出し、押されたら文字で app を呼ぶだけ** |
| `launchd/`・`cloud/` | **常駐の配線**——時計のひと回りと AI のひと回りを周期で起こす（手元は launchd、クラウドは Cloud Run Jobs と Scheduler）。**買った仕組みの設定であってコードではない**（時計の表に「AI を起こす」は増えない） |
| `tests/` | 赤くする仕掛け |
| `custom/<題材>/` | 題材（`Topic`）のデータ。**コードにしない**（実行時の帳簿は `data/`——コミットしない） |

**まとめかたはパターンの名、ファイルは業務の概念**（人の判断）——values・aggregates・events・services に1概念1ファイル。承認なら値 `Approval`・操作 `approve`・出来事 `Approved` がそれぞれの棚に1枚ずつ。
**操作は、引数の型が「から」・返りの型が「へ」・返りは必ず（次の姿, 出来事）の対**——I1 と遷移表が型になり、突合が設計の表と署名を1行ずつ照合する。
**集約が境界**——`job → rule → 暦・人 → 義務` の一方向を依存の契約が守る。**業務ルールは仕事を知らない。**

**この表に無いファイルを作らない**——`utils`・`helpers`・`common` が生まれるのはここが緩いとき。**ファイル名は設計の語**——`ls domain/` で業務に何が在るか読めること。

## 6. 赤くする仕掛け

**種類が偏ったら未完成。** 前回の7つは全部「名前と住むところ」で、
「型が正しさを保証しているか」を見るものが1つも無かった。

| 種類 | 何を守るか |
|---|---|
| **型** | 不正な値・不正な状態が**書けない** |
| **自動試験** | 例が仕様。この材料ならこうなる |
| **突合** | 設計の表と実物が一致しているか |
| **人** | 誰がいつ読むかまで書けるものだけ |

**「壊して赤を見た」を書いていないものは、置いたと言わない。**

実装を始めるときは**この順で置く**——値の義務・禁止値・禁止状態が先。
前回はここを最後まで置かなかった。

## 7. いつ設計をやめて、コードを書き始めるか

**設計を完成させてから作る、をやめる。** 前の一座は19枚80ファイルまで行って、
**本物の1週を一度も通さずに**捨てた。いまも5回なぞって0行。
**動かさないと分からないことを、設計で決めようとしている。**

### 止まりを2つに分ける

ロールプレイが見つける止まりは、性質が2つある。**閉じるのは片方だけ。**

| 種類 | どういうものか | どうするか |
|---|---|---|
| **設計が要る** | 矛盾している／材料がどこにも無い／置き場が無い／循環している | **閉じる** |
| **実装で決める** | 値の具体・並び順の細部・文言・どの型で表すか | **閉じない。「実装で決める」と書いて残す** |

**全部を閉じるのは不可能**——敵対的に読めばいくらでも出る。
**閉じるべきものだけを閉じる。**

### 収束のポイント

次の3つが揃ったら、設計を止めてコードを書き始める。

| 条件 | 測りかた |
|---|---|
| **うまくいく週が最後まで通る** | ロールプレイの「週Aをなぞる」が、止まり0で最後まで行く |
| **残った止まりが「実装で決める」だけ** | 「設計が要る」に分類される止まりが0 |
| **設計が5枚・1000行を超えていない** | 超えたら足さない。足すなら何かを消す |

**落ちる週（週B）は通らなくてよい。** 落ちる週まで設計で通そうとすると、
起きてもいないことを決めることになる。**動かして、実際に落ちてから直す**——実際に落とした筋書きは固定テストが守る。

### 書き始めたあとの決まり

| 決まり | なぜ |
|---|---|
| **設計は5枚・1000行を超えない。** 足すなら何かを消す | 2000行で散った。上限が無いと必ず膨らむ |
| **赤くする仕掛けは、コードと同時に置く** | 設計の段で全部「まだ居ない」のままにすると、最後まで置かれない（前回そうなった） |
| **週Aが通ったら、次は週Bではなくコード** | 動くものを先に。落ちる週は動かしてから |
| **動かして分かったことは、設計に戻す** | 戻さないと、また設計とコードが離れる |

## 8. 書き終わりに確かめること

1. 執行者の欄に空が無いか
2. 分類の行に義務が書けているか
3. 数を2箇所以上に書いていないか
4. 用語集に業務以外の語が入っていないか
5. **前の文書と食い違っていないか**——食い違ったら**前に戻る**。いまの文書で辻褄を合わせない
6. 壊して赤を見たか
7. **その1枚の中で閉じているか**——閉じないなら、割り方を疑う

**5と7がいちばん大事。** 前回は食い違うたび but 書きを足して辻褄を合わせ、
その積み重ねが「設計は正しいのに実装が合っていない」を作った。
