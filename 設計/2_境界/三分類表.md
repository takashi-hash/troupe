## 1. 三分類 ―― 力の注ぎ先

| 分類 | 領域 | 扱い | なぜ |
|---|---|---|---|
| **CoreDomain** | Job の一生（State と Lease）／Checkpoint／Reconciliation／Definition の Version と Gate／Evidence と Closed／Verification の2層／Ledger という場 | **作り込む。最良の時間を注ぐ** | 「自律する仕事場」の自律はここでしか生まれない |
| **Supporting** | 題材の Custom の中身（順は 運転→庶務→訪問診療——ドメインモデル §10）——Definition の中身・Checkpoint の位置・Sensitivity の業務ルール・ReadPort の中身 | Foundation の型に**注入する形**で作る。Foundation 側には1行も書かない | 現場に必須。ただし Foundation の価値ではなく、題材ごとに入れ替わる |
| **Generic** | LLM 実行基盤／通知／認証／GUI 部品／保存の仕組み | **買う・借りる。作り込まない** | どこにでもあり、競う意味がない。作ると CoreDomain から時間を奪う |

**判断軸は1つ**: それが優れていることに、この仕組みの存在理由があるか。あるなら CoreDomain。無いなら Supporting か Generic。

**機械的に書けることは、CoreDomain でない理由にならない。** 価値は行数ではなく掟にある——骨組み（State・Lease・再試行）は小さく書けるが、掟（誰が approve できるか・何で閉じるか・何が二度起きないか）は買ってこられない。CoreDomain とは「Job の一生」の骨組みではなく、**一生に有効な掟**のこと。

## 2. どの言葉がどの Boundary のものか

| Boundary | 言葉の持ち主 | 例 |
|---|---|---|
| Foundation | [用語集](../1_言葉/用語集.md)（有効になった語のすべて） | Job・Lease・Checkpoint・Reconciliation・Evidence |
| Custom（いまは運転） | Board の Constitution | リポジトリ・依存・検査の結果（診療期には施設・担当医が並ぶ） |
| 各 Source | Source 自身（こちらは変えられない） | git の言葉・check の結果の言葉・依存一覧の言葉・Calendar の言葉（診療期にはカルテ・レセコンが並ぶ） |

- Foundation の言葉に現場の言葉を混ぜない。現場の言葉に Source の言葉を混ぜない
- Source の言葉は **ReadPort が翻訳して** Foundation の言葉に直す。翻訳せずに持ち込んだらそれは Boundary の破れ
