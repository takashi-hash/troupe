# Ichiza（一座）— 部品一覧

**版**: v2.2（2026-08-21。v2.2: Alert の導出元を直した——Event の列からではなく、State と Version と承認の数から（状態だけでは CheckpointBypassed が見えない）。v2.1: v2.1: 証拠は源から読んだ引用でできる。v2.0: v2.0: 術語を識別子に統一——読みかた 掟9）
**状態**: **有効になった**（2026-08-21、人が有効化した）

対象は CoreDomain の言葉すべて（[用語集](../1_言葉/用語集.md)）。判定は「**値にできないか、を先に疑う**」の順。
仕分けは3つ: **同一性が本体**（変わり続けても同じもの）／**値が本体**（不変。直すなら新しい値）／**部品ではない**（行為・状態・規則・場——扱う歩を明記）。

---

## 1. 同一性が本体のもの

| 識別子 | 同一性の根拠 | 迷った理由 |
|---|---|---|
| Participant | 申告が変わっても同じ者。信頼（AgreementRate）は個体に積み上がる | 同名の新プロセスは同じ Participant か → **登録が同一性、プロセスは器** |
| Board | Constitution が Version を重ねても同じ場 | — |
| Job | 一生の State が変わり続けるものは値にできない | ChildJob は独立した Job（親への参照を持つ）。親の分身ではない |
| Definition | **名**が Version の列を束ねる。Version が積まれても同じ Definition | Definition＝名（同一性）、Version＝値 |
| Proposal | 作成される→enact／却下の経過を生きる。**却下の再発を弾くには同一性が要る** | 同一性の鍵は **Fingerprint**——同じ中身の再提案は同じ Proposal |
| Source | 登録された Source は、ReadPort の契約が変わっても同じ Source | Calendar も Source（登録は Foundation が既定で持つ） |
| ReadPort・WritePort | 契約の Version を積む登録物 | 契約の形は歩7（口の型は domain に、実装は adapters に） |

## 2. 値が本体のもの

| 識別子 | 不変の根拠 | 迷った理由 |
|---|---|---|
| CapabilityDeclaration・RoleDeclaration | 名乗った時点の写し。変われば新しい申告 | 照合＝申告（値）と実態の突き合わせ、と読み直せる |
| Version | 「積むだけ・上書き無し」そのもの | — |
| Constitution | freeze された1枚は不変。直しは新しい Version | freeze 前の下書きは有効でない（Proposal と同じ扱い） |
| AcceptanceCriteria | Constitution・Definition の中の不変の記述 | — |
| 時刻の対（ready_at, Deadline） | **2つの時刻の対**。変更は新しい対 | 「緊急フラグは作らない」が型になる場所 |
| Lease | holder と期限の対。取り直しは新しい Lease | Lease の履歴は Event が持つ（Lease は「現在」だけ） |
| Briefing | dispatch した時点の包み。直すなら詰め直して新しい Briefing | 中身は参照で持つ（§5） |
| Artifact | 置かれたら不変。直しは新しい Artifact | Evidence が指すのは特定の1つ——これで I5 が成り立つ |
| Event（Progress・Discrepancy を含む） | 起きた事実の観察。積むだけ | — |
| Evidence | 引用と Fingerprint。後から変わるなら Evidence ではない | **引用は源から読んだ中身そのもの**——読み口が無い仕事は SelfReport（確かめの期限つき）に落ちる |
| Budget | Definition が決める量と時間の対 | — |
| Checkpoint の位置 | Definition の中の指定 | Checkpoint の「待ち」は Job の State（歩6） |
| Utterance | 言った事実。消えない（口約束が消えない） | Conversation は Utterance の列。束の同一性は Job・Proposal への紐で足りる |
| SensitivityMark | Source の登録に付く性質 | 何が Sensitivity かは Custom の中身 |
| Alert | 導出された判定の写し。**元は Job の State と Version と承認の数**（Event の列からではない——状態だけでは `CheckpointBypassed` が見えないので、版と承認の数も要る） | 保存か導出かは歩5・7（導出に決着）。判定は surface の1箇所（`domain/alert.py`） |
| MorningSheet | 導出された読み物。保存しない | 形は歩7（読む枚に決着。のちに検索を追加） |

## 3. 部品ではないもの（行き先つき）

| 語 | 何か | 扱う歩 |
|---|---|---|
| Ledger | 場。部品の入れ物 | 歩4（Aggregate か Space か → Space に決着） |
| Gate | 規則（Constitution の状態から導く） | 歩5（三分解 → 不変条件） |
| enact・Reconciliation・翻訳・照合 | 行為 | 歩5（調停）・歩6（操作の型） |
| Created〜Failure の状態 | Job の State | 歩6（型） |
| Boundary・CoreDomain・Supporting・Generic・Foundation・Custom | 設計の言葉。動くものではない | — |
| Location | 語だけ確保 | 決めない（決定済み） |

---

## 4. ID の採番

- ID は**立てた者が、立てた瞬間に振る**——Definition 発は Manager、Instruction 発は Reception、ChildJob は親の Worker
- **ID に意味を持たせない**（意味は変わる。意味は中身が持つ）
- Proposal だけは ID と別に **Fingerprint** を持つ（却下の再発を弾く鍵）

---

## 5. Briefing の中身（未決#7への結論）

必ず携えるもの（**すべて参照で指す**。重い中身は Artifact と Source に置く）:

1. 何をするか — Definition の該当 Version への参照
2. 読むべき Source — ReadPort と範囲
3. 材料 — 先行の Artifact への参照
4. Artifact の置き場
5. AcceptanceCriteria への参照
6. Budget
7. Board の言葉 — Constitution への参照（モデルの注入）

- **型は Definition が決め、詰めるのは立てた者**（ID と同じ分担）
- 参照で持つから、「Briefing の無い Job は dispatch できない」は**参照が解決できるかの機械判定**にできる——つまり Check（止める力）にできる
