## 0. 実装言語の決定

**Python に決定**（2026-08-21。**同日の TypeScript の決定を名指しで覆す**）。選定条件「状態ごとに持ち物が違う型・終端状態・網羅のチェックを素直に書けること」（[禁止状態一覧](../6_型/禁止状態一覧.md)の申し送り）は次で満たす:

- **pydantic の frozen＋判別可能ユニオン**——実行時にも不正な値を弾く。「書けなくする」が動いている最中まで届く（型が消える言語より強い）
- **pyright（strict）の網羅チェック**——State の取りこぼしを赤くする
- **監査する人が読める言語であること**。判断は Human——enact する人が中身を読めるのは、好みではなく要件
- ローカル LLM 周辺の道具に最も近い言語圏
- 「画面まで1言語」の利点は、**画面も Python で描く**（ネイティブ GUI——10_画面 §0）ことでそのまま保つ

**条件3つ**: uv で環境管理／pydantic＋pyright strict を必須（禁止状態の実装条件）／画面も Python で描く。

**組み立ての根も検査に入れる**（2026-08-21）: `main.py` は型検査にもテストにも入っておらず、その死角で**申告と申告を突き合わせる偽の照合**が生きていた（実在しない業務ルールと口を申告し、同じ文字列を実態として渡していた）。いまは pyright の対象で、`tests/test_startup.py` が見る。

**実行の足場**: 配布先は手元の Mac 2台——git と uv で足りる（単一バイナリは不要）。起動は launchd で、**宣言ファイルをリポジトリに含めるまでが実装**（宣言に執行者がいなければ実装ではない）。
→ `launchd/org.ichiza.plist`（2026-08-21 に用意。入れる手順はファイルの先頭に書いてある）

**例外と値の作法**（2026-08-21 決定）: **domain の操作は例外で拒む**（`CannotTake`・`IllegalTransition`——
Python では例外の方が読みやすく、呼び忘れが起きない）。**層の境目で値に変える**——app の輪と働き手は
例外を外へ逃がさず、帳簿の出来事と状態（EnvironmentFailure／ContentFailure）に落とす。
つまり「失敗を値として持つ」のは**帳簿の中**であって、関数の戻り値ではない。

**識別子の掟**（読みかた 掟9）: 設計文書とコードは識別子で書き、日本語の語との対は**用語集だけが持つ**（1語1識別子の全単射。勝手訳の禁止）。型と関数の docstring に日本語の語を書く——grep の錨。

## 1. 4つの層（依存は内向きのみ）

**層とフォルダの名前は構造であって、語彙ではない。** 一座の術語（識別子）は型・関数・テスト名の側に置く——混ぜない。

| 層（＝フォルダ名） | 住むもの | 知ってよいもの |
|---|---|---|
| **domain/** ——掟の住む中心 | Aggregate 6つ・状態モデル・Check の型・不変条件・**口の型**（LedgerPort・ReadPort・WritePort・LlmPort） | **何も知らない**。LLM も Source も保存も画面も知らない |
| **app/** ——回す係 | Manager の7つの輪・Reception・dispatch の Check・Briefing 詰め | domain と、そこにある口の型だけ |
| **adapters/** ——口の実装 | Ledger の保存（Aggregate の State＋AppendOnlyLog＋Artifact＋**Evidence**）・**Source ごとの ReadPort（検査の結果・依存の一覧・git）**・WritePort・LLM 実行基盤への接続・Calendar | domain の口の型を実装する（逆向きの依存はここで折り返す） |
| **ui/** ——読む5枚と Chat | MorningSheet・Outlook・History・SearchSheet・JobSheet・Chat | 参照専用の読み口と、**app の surface**（判定は1箇所から読む——画面側で判定しない）。**domain の型を画面に直接返さない**（導出関数が返すのは画面用の値）。書くことは全部、Utterance として Ledger に落ちる（Reception が拾う） |

**置いてはいけないもの**（知ってよいものの裏。こちらの方が効く）:

| 層 | 置いてはいけないもの |
|---|---|
| **domain** | **時計・乱数・保存・画面・道具**。「いま」は引数で受け取る——時計を持った瞬間、テストが決定的でなくなる |
| **app** | **業務の規則。** `if` で業務の判断を書きたくなったら、それは domain に置くべき規則 |
| **adapters** | **業務の規則。** 翻訳と入出力だけ |
| **ui** | **業務の規則。** 並べる・整える・受け取るだけ |

「業務の規則を置いてはいけない」が3層に書いてあることが要点——**規則が置けるのは domain だけ**。

- **口の型は domain に、実装は adapters に。** これが依存を内向きに保つ唯一の仕掛け（構成要素ごとの置き場は §5）
  ——**読み口も同じ**（2026-08-21。SheetSource が ui に在ったせいで app の輪から画面の材料に触れられず、判定が画面の中に落ちた。層の間違いがそのまま掟破りを呼んだ）
- 鍵（Source への認証）は**口の実装が持つ**。domain にも Agent にも渡らない（未決#2への結論）
- WritePort は**冪等の鍵**を受け取れる相手にはそれを渡す——Apply の二相と合わせ、二重の実行を口の側でも弾く
- **口と Tool の実装の規格は MCP**。ReadPort・WritePort・Tool は MCP サーバとして立て、CapabilityDeclaration の「手の届く範囲」は**繋いでよいサーバの一覧**になる。domain は MCP を知らない（借り物——語彙に数えない）。既製の MCP サーバはそのまま Tool として使える
- **LLM 実行基盤は Ollama を既定に**（Generic＝買う）。LlmPort で包むので、差し替えは口の実装1枚。**どのモデルを載せるかは決めない**——CapabilityDeclaration と AgreementRate の実測で決める

## 2. 人が読む5枚（未決#3・#4への結論）

役割の違う5枚。すべて**導出**（保存しない）。判定は surface の1箇所から読むだけ。**画面に出す言葉は日本語の語**（読みかた 掟10——出してよい語は用語集 §10）。

| 枚 | 答える問い | 中身 |
|---|---|---|
| **MorningSheet**（画面名: 今日） | 「今日、私の判断と目が要るものは？」 | surface が判定した Alert だけ——**`CheckpointBypassed`・裁く版が引けない**（赤）／ContentFailure（赤）／担当の Checkpoint／宛先の AwaitingAnswer／SelfReport の確かめ期限／Deadline が今日・過ぎた Job。**EnvironmentFailure は出さない**（再試行の最中で人が今できることが無い）。**先の予定も載せない**——載せると赤が埋もれて読まれなくなる |
| **Outlook**（画面名: 予定） | 「先に何が来る？」——月・週・日で切り替えて見る | ①作成済みの Job（ready_at と Deadline で並ぶ。明日やる Job もここに見える） ②**まだ作成されていない予定**——Definition×Calendar から導く。翌月の請求は、作成される前から見える |
| **History**（画面名: 履歴） | 「過去に何を頼み、何が済んだか？」 | AppendOnlyLog から——Utterance・Origin（誰の Instruction で作成済みか）・**JobClosed と Evidence（完了は証拠つきで並ぶ）**。次に頼むときの材料 |
| **SearchSheet**（画面名: 検索） | 「あのタスクはどこ？」——**完了したものも含めて** | すべてのタスクから、モデルの欄で絞って引く（キーワード・状態・業務ルール・担当・期限）。**他の枚から落ちたものを拾うのが役目**——キーの一覧と導き方は 10_画面 §3.5 |
| **JobSheet**（画面名: 詳細） | 「この Job は、誰が・いつ・何を・どうした？」 | 1つの Job の全部——Origin・State と時刻の対・**Event の列を job_id で絞った時系列**（Lease の holder、Progress、Check と Review の結果、approve した人と時刻、差し戻しの理由）・Briefing が指した Source・Artifact・Evidence。**I5「説明できる」を画面にしたもの** |

- **MorningSheet だけが押しつけ**（毎朝出る）。残る3枚は**引き出し**（見たいときに見る）。この分け方が狼少年を防ぐ
- JobSheet は、他のどの枚からも Job を1つ選べば開く（Outlook の予定を選んだときは、まだ Job が無いので Definition の該当 Version を見せる）
- 予定はまだ Job ではない。早く始めたければ Instruction として頼めば Reception が create する
- 毎回同じ Alert・件数だけの飾り・母集団の違う数字の並びは、どの枚にも載せない

## 3. Chat（画面名: チャット）

読む5枚とは別に、**Chat** が1つ。ここだけが読み書き両方。すべての Utterance は Ledger に落ちる（口約束が消えない）。

**Human → Agent**（Reception が Utterance を3種に仕分ける）:

| Utterance の種類 | Reception がすること |
|---|---|
| Instruction（これやって） | Job に写す。Origin＝Utterance、ready_at＝指示の時（無ければ今） |
| 業務の追加・変更（これからは毎月◯◯して） | **Definition の Proposal** に写す。enact するのは Human——「enact して」までこの口で言える |
| 質問（あれどうなってる？） | Ledger から答える——JobSheet・Outlook・History を引いて Utterance で返す。**決め方は言わない** |

**Agent → Human**（自律の側からの口）:

| 何が来るか | 出どころ |
|---|---|
| **Inquiry** — Job の途中で材料が欠けたときの問い | Worker。Job は **AwaitingAnswer** で止まり、answer が来たら続きから動く |
| 判断の材料 — CheckpointReached のとき | Manager（MorningSheet と同じ判定から） |
| ProposalCreated | Worker 発。Human の enact 待ち |

- **Inquiry は判断のお伺いではない**（判断を求めるのは Checkpoint だけ）。材料の欠けを埋める問いだけ。inquire する前に Source と Briefing で自分で調べたか、は Review の観点になる
- 答えは Utterance としてその Job に紐づき、**Evidence になる**——「なぜそうしたか」に「あなたがこう答えたから」が残る

## 4. 実装初日にやること（この順で）

1. **依存方向のテスト**——層の逆流を赤くする。最初のコードより先に
2. 状態モデルを型に写し、**禁止状態一覧の1行ずつが「書くと落ちる」ことを確かめる**
3. Check を書いたら**壊して赤を見る**（I6）。赤くならない Check は入れない
4. AcceptanceCriteria と禁止状態は、**具体例のままテストにする**（例が仕様）
5. **対訳 lint**——**全層**に①和名の識別子が現れたら赤 ②公開の型・関数の名前が用語集に未登録なら赤 ③docstring に対応する日本語の語が無ければ赤（grep の錨）。用語集の執行者はこの lint（tests/glossary_lint.py）。②の例外は**道具の構造の名だけ**で、lint の `TOOL_NAMES` に理由を1行添えて並ぶ——その抜け道は adapters/ と ui/ でしか効かない（domain と app に道具は無い）

### 置き場を決めるときの1本の問い

**「これは業務の規則か、回す手順か」**——規則なら domain、手順なら app。
迷う形は3つあり、全部この問いで割れる:

- **新しい1件の形**（期限の決め方・写す量）は規則 → Factory は domain。
  ただし**採番は手順**（誰が立てたか）→ app が振った ID を Factory が受け取る
- **どの集約のものでもない規則**（合格か・何が赤か）は規則 → DomainService は domain。
  「集約に持ち主がいない」ことは、app へ落とす理由にならない
- **並べる順・件数・見出し**は手順でも規則でもなく**見せ方** → ui

### 口の名は、接尾辞で役割を言う

`domain/ports.py` の Protocol はすべて**口**。どの口かは接尾辞で読める:

| 接尾辞 | 役割 | いま |
|---|---|---|
| `*Repository` | 集約ルートの出し入れ（ルートごとに1つ） | Job・Definition・Board・Participant |
| `*Store` | 積むだけの列の置き場（積む・読み出すだけ） | Artifact・Evidence |
| `*Port` | 外の道具・外の世界 | Llm・Source・Custom・Ledger |
| `*Source` | 参照専用の読み（守るものが無い） | Sheet |

**いまは全部合っている**（2026-08-21、段A1 で `EventLog` を `EventStore` に直した）。
規則が無かったあいだ、同じ「置き場」という語が **Repository・Store・Log の3通りの英語**に
化けていた——接尾辞に意味を持たせると、名前だけで役割が読める。

### 集約の操作と、そうでないものの見分け

**集約の操作は閉じている**——その集約を受け取って、**同じ集約を返す**
（`approve(job) → Job`・`close(job, …) → Job`）。閉じているかどうかで機械的に割れる:

| 形 | 何か | 置き場 |
|---|---|---|
| `X → X` | 集約の操作 | その集約の隣 |
| `部品 → 真偽` | **仕様** | domain |
| `いくつかの集約 → 判定` | **DomainService** | domain |
| `帳簿 → 帳簿への書き込み` | **ApplicationService** | app |

### DomainService は逃げ場になる（歯止め）

置き場に迷ったものを全部ここへ入れると、集約が痩せて DomainService が太る。
**先に「その操作の主語は誰か」を問う**——主語になれる集約があるなら、そちらの操作にする。
主語が「一座そのもの」としか言えないときだけ DomainService。

数えて確かめられる: **domain の DomainService が集約の数を超えたら赤信号。**
いまは集約6・DomainService 1つ（`alerts_for`）——足りている。
`check` を DomainService だと書いたのは取り違えで、あれは**仕様**（部品を受け取って真偽を返す）。
**役割に名が無かったから取り違えた**——名が無ければ、数えることも間違いに気づくこともできない。
ただし `matches`・`assignee_of`・`definition_of`・`period_of` は**主語が Job** なので、
Job の隣へ移した（2026-08-21、段A3）。`search.py` に残るのは検索条件と仕様だけ。

## 6. いま内向きから外れている3つ（2026-08-21 の点検）

**依存の向きは守れている**——domain は何にも依存せず、時計も乱数も保存も持たない
（「いま」は全部引数で受け取る）。口の型は domain、実装は adapters。執行者は import-linter。
ここは動いている。**外しているのは向きではなく、層ごとの責務**で、3つある。

### 1. トランザクションの境目が adapters にある

いま `BEGIN IMMEDIATE` は置き場の `put` の中で開いて閉じる。
**置き場は「1回の保存」しか知らず、ひと仕事の範囲を知らない。**

見えている実害: `inject` はボードと複数の業務ルールを**別々のトランザクション**で書く。
途中で落ちれば半分だけ入る（冪等なので入れ直せば揃うが、それは別の性質で塞いでいる）。

あるべき: ひと仕事＝ひとトランザクション。境目を握るのは app。

### 2. 画面がドメインの型をそのまま受け取っている

`SheetSource.all_jobs()` は `Job`（集約そのもの）を、`surface` は `Alert` を画面へ渡す。
`ui/sheets.py` は domain から6つ import している。

**依存の向きとしては合法**（外側は内側に依存してよい）。外しているのは別の線で、
**境界を越えるときは「ただの値」に詰め替える**という規律。いまは Qt に渡す手前で
`Row`・`Section` に詰め替えているが、詰め替えているのは ui 自身。

見えている実害: 画面が集約の形を知っているので、**ドメインを直すと画面が壊れる**。
`ui/sheets.py` が大きいのも、集約を受け取っているから。

あるべき: 詰め替えは app。画面には「文字と ID」だけが届く。

### 3. 参照の経路が集約を通っている

`all_jobs()` は**全部の Job 集約を読み戻して**から、画面が Python で絞る。
集約は「不変条件を守る」ための形であって、「並べる」ための形ではない。

更新と参照は別の経路でよい——**参照は集約を経由せず、画面に要る形をそのまま返してよい**
（SQL を直に書いてよい・表を跨いでよい）。守るものが無い読みに、集約の形は要らない。

見えている実害: いまは件数が少ないので動く。`all_jobs` の説明に
「遅いと**実測**できたら SQL 側へ移す」と自分で書いてある——**形の問題を速さの問題として先送りしている**。

### この3つの扱い

**どれも「いま壊れている」ではなく「いま効いていない」**。
1 は入れ直しで揃い、2 は画面が小さいうちは直せ、3 は件数が少ないうちは速い。
だから急がない。ただし**3つとも、大きくなってから直すのが最も高い種類**なので、
実装を再開したら §5 の申し送り（Factory を domain へ・この表の執行者）の次に置く。
