# Ichiza（一座）— モデリング計画

**版**: v0.3（2026-08-21。v0.3: 術語を識別子に統一——読みかた 掟9）
**状態**: **7歩すべて完了**（2026-08-21）。以後この文書は経緯の記録。
**掟**: 実装はモデリングが終わってから。一気に進めない。1歩ずつ、各歩に成果物と完了条件を置く。

---

## 0. 進んだ順

> **言葉 → Boundary → 部品 → Aggregate → Event → 型 → 配置**

- 先に全体（言葉と Boundary）を固め、それから中身（部品と Aggregate）に入る。配置と言語の決定は最後
- 分類や実装から始めない。効果が見えないまま工数だけ増える

---

## 1. 用語集 ―― 言葉を1つにする

- 概念それぞれに一言定義。あいまいさを潰し、**同義語を残さない**
- 言語は「決める」ものではなく「発見する」もの。既にある文書から掘り出す
- 結論: 用語集は人も Agent も読む**土台の言葉**。現場の言葉は Constitution が持つ（入れ子）

**成果物**: `1_言葉/用語集.md`（のちに全語へ識別子を割当——日本語⇄識別子の唯一の橋になった）
**完了条件**: 以後の会話とドキュメントで同じ語しか使っていない。新語が出たら用語集に戻す運用が回っている。

---

## 2. 三分類と Boundary ―― 線を引く

- 三分類: CoreDomain（Job の一生・Checkpoint・Evidence・Reconciliation）／Supporting（訪問診療 Custom——当時の想定。のちに Custom の順は 運転→庶務→訪問診療 に決定、ドメインモデル §10）／Generic（LLM 基盤・通知・認証——買う）
- Source（カルテ・レセコン・支払基金・Calendar——当時の想定）は外部。ReadPort が翻訳する
- Boundary を跨ぐ言葉は必ず翻訳される

**成果物**: `2_境界/三分類表.md`・`コンテキストマップ.md`
**完了条件**: どの概念がどの Boundary に属すか即答できる。

---

## 3. 部品の識別 ―― 同一性か、値か

- 判定は「**値にできないか、を先に疑う**」の順
- 同一性: Job・Participant・Board・Definition・Proposal・Source・口
- 値: Version・Constitution・Lease・Briefing・Artifact・Event・Evidence・時刻の対ほか
- Briefing の中身7項目（すべて参照で指す）と ID の採番もここで決着

**成果物**: `3_部品/部品一覧.md`
**完了条件**: 全概念がどちらかに置けて、迷いの理由が書き残してある。

---

## 4. Aggregate と不変条件 ―― 山場

- I1〜I8 を「どの Boundary の内側で守るか・即時か結果か」に割当
- Aggregate は6つ（Job・Definition・Board・Participant・Proposal・SourceRegistration）。Ledger は Space
- Lease の取り合いは版で決着。Gate は dispatch の Check。親は子の一覧を持たない

**成果物**: `4_集約/集約境界図.md`・`不変条件対応表.md`
**完了条件**: 「このルールはどこに書けるのか」に全不変条件が答えを持つ。1回の書き込みは1 Aggregate。

---

## 5. Event と調停 ―― Aggregate の外側

- Event カタログ（すべて過去形）。履歴を Event の列としては持たない（結論）
- Manager の5つの輪（create・patrol・confirm・triage・surface）——全部冪等。create の鍵は **Origin**
- 規則の三分解: 不変条件／仕様（Check・Review・AcceptanceCriteria）／ポリシー（Definition）

**成果物**: `5_出来事/` の3枚
**完了条件**: 「誰も直接話さない。全部、Ledger 越し」が Event の列で言い直せる。

---

## 6. 型で表現不能にする ―― Job の一生の型モデル

- State ごとに持ち物が違う型。禁止状態を「書けない形」に
- Check と Review は別の型。Failure は Environment と Content に割れる
- Apply の二相（Attempt → 実行 → 結果）と Sensitivity の take 制約もここに

**成果物**: `6_型/状態モデル.md`・`禁止状態一覧.md`
**完了条件**: 禁止状態が「注意書き」でなく「書けない形」になっている。

---

## 7. 配置と形態 ―― 実装への橋

- 4層: domain／app／adapters／ui。依存は内向きのみ。口の型は domain、実装は adapters（MCP）
- 読む枚（MorningSheet・Outlook・History・JobSheet。のちに SearchSheet を追加）と Chat。押しつけは MorningSheet だけ
- 実装言語: Python（uv・pydantic・pyright）。LLM 基盤: Ollama。起動: launchd

**成果物**: `7_配置/層割当て表.md`・`形態マップ.md`
**完了条件**: 「何を作らないか」が「何を作るか」と同じ精度で書いてある。

---

## 8. 各歩の終わりに ―― 自己レビュー

- 同義語が生まれていないか（言葉のずれ）
- 規則が Boundary の外に漏れていないか
- 書いた宣言に執行者がいるか（読む者のいない欄を作っていないか）
- Generic を作り込んでいないか
- 依存が内向きか
- 画面の形とモデルを混ぜていないか

## 10. やらないこと

- **複数サービスへの分割** ―― まず1台は決定済み
- **Event の列から State を組み立て直すこと** ―― 既定どおり不採用で決着（歩5）
- **全部の分類から始めること** ―― 効果が見えないまま工数だけ増える。だから歩1・2が先だった
